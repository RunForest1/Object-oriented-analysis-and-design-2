# Лабораторная работа №4: Архитектурный паттерн «Предварительная загрузка» (Lazy Load)

## Система управления задачами «ToDo List» с оптимизацией загрузки данных

---

## Назначение и Проблема

В приложениях со сложными объектами, содержащими большие объемы связанных данных (например, список дел **ToDo**, внутри которого может находиться сотни задач **Task**), прямая загрузка всех данных при создании основного объекта приводит к серьезным проблемам производительности.

**Традиционный подход («жадная загрузка», Eager Loading):**
- При запросе объекта `ToDo` из базы данных сразу же подгружаются все связанные с ним записи `Task`
- Если пользователю нужно просто отобразить список названий дел без деталей, система все равно выполнит тяжелые SQL-запросы (JOIN или отдельные SELECT)
- Загружаются гигабайты ненужных данных в память
- Замедляется отклик интерфейса
- Неэффективное использование ресурсов CPU, RAM и сети

### Решение: Паттерн Ленивой Загрузки (Lazy Load)

Идея заключается в том, чтобы откладывать загрузку тяжелых связанных данных до момента, когда они действительно понадобятся программе.

## Сравнительный Анализ

### Таблица Сравнения: Lazy Load vs Eager Loading

| Критерий | С паттерном Lazy Load | Без паттерна (Eager Loading) |
|----------|----------------------|------------------------------|
| **Момент загрузки данных** | Отложенный: данные подгружаются из БД только в момент первого обращения | Немедленный: все связанные данные загружаются при создании родительского объекта |
| **Производительность (Start-up)** |  Высокая: инициализация быстрая, нет тяжелых I/O |  Низкая: долгое ожидание ответа БД |
| **Использование памяти (RAM)** |  Экономное: только используемые объекты |  Расточительное: загружается всё, даже ненужное |
| **Нагрузка на БД** |  Оптимизированная: запросы только при необходимости |  Избыточная: сложные JOIN-запросы независимо от потребности |
| **Сложность реализации** |  Выше: требуется логика проверки состояния |  Ниже: простой маппинг БД-объекты |
| **Проблема N+1** |  Риск возникновения в циклах |  Отсутствует (данные в одном запросе) |
| **Масштабируемость** |  Отличная |  Плохая |
| **Сетевой трафик** |  Минимум: только нужные данные |  Максимум: один огромный пакет |


## Выводы по Лабораторной Работе

**Оптимизация ресурсов**
- Внедрение паттерна Lazy Load позволило значительно снизить время отклика приложения при отображении списков
- Избежана ситуация, когда для показа 10 названий задач система загружала из базы 10 000 строк с описанием
